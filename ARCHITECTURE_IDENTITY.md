# Архитектурное решение: Управление учётными данными пользователя

## Обзор решения

Архитектурное решение для управления учётными данными пользователя в системе BionicPRO обеспечивает:
- Унификацию доступа через внешние Identity Providers в разных странах
- Локальное хранение персональных и медицинских данных
- Безопасную работу с токенами без передачи их фронтенду
- Поддержку различных внешних удостоверяющих служб

## Компоненты архитектуры

### 1. Backend for Frontend (BFF) Service

**Назначение**: Промежуточный слой между фронтендом и бэкенд-сервисами, обеспечивающий безопасную работу с токенами.

**Функции**:
- Обработка OAuth 2.0 Authorization Code Flow
- Управление сессиями пользователей
- Выдача session cookies вместо токенов IdP
- Проксирование запросов к API с подстановкой токенов IdP

**Технологии**: Spring Boot, Spring Security

### 2. Identity Provider Gateway

**Назначение**: Абстракция над различными Identity Providers, обеспечивающая единый интерфейс для работы с разными IdP.

**Функции**:
- Маршрутизация запросов к нужному IdP в зависимости от региона пользователя
- Адаптация протоколов различных IdP (OAuth 2.0, SAML 2.0, OpenID Connect)
- Управление конфигурацией IdP по регионам
- Плагинная архитектура для добавления новых IdP

**Технологии**: Spring Boot, Spring Cloud Gateway

### 3. Token Service

**Назначение**: Централизованное управление токенами от Identity Providers.

**Функции**:
- Безопасное хранение access- и refresh-токенов (AES-256 шифрование)
- Автоматическое обновление токенов при истечении
- Выдача собственных JWT токенов для внутренних сервисов
- Валидация токенов на каждом запросе
- Аудит использования токенов

**Технологии**: Spring Boot, Redis (для хранения токенов)

### 4. Local Identity Store

**Назначение**: Локальное хранилище учётных записей пользователей.

**Функции**:
- Хранение минимально необходимых данных для идентификации
- Связь внешних идентификаторов (из IdP) с внутренними ID пользователей
- Хранение метаданных о пользователе (регион, IdP, права доступа)
- Обеспечение изоляции данных по регионам

**Технологии**: PostgreSQL

**Принципы хранения**:
- Минимизация данных: только идентификаторы и метаданные
- Персональные и медицинские данные хранятся отдельно в региональных БД
- Соблюдение принципа data residency

### 5. Regional Identity Providers

**Назначение**: Внешние удостоверяющие службы в разных регионах.

**Региональные IdP**:
- **Россия**: Keycloak (локальный или облачный)
- **Европа**: Azure AD, Okta (с соблюдением GDPR)
- **США**: AWS Cognito, Auth0 (с соблюдением HIPAA)
- **Другие регионы**: Гибкая конфигурация через IdP Gateway

## Поток аутентификации

### 1. Инициализация аутентификации

```
Пользователь → Frontend → BFF Service
```

Пользователь открывает фронтенд, который делает запрос к BFF для аутентификации.

### 2. Определение региона и IdP

```
BFF Service → Identity Provider Gateway
```

BFF определяет регион пользователя (по IP, настройкам или явному выбору) и запрашивает у IdP Gateway соответствующий IdP.

### 3. Перенаправление на IdP

```
BFF Service → Identity Provider Gateway → Regional IdP
```

Пользователь перенаправляется на соответствующий IdP для аутентификации.

### 4. Аутентификация в IdP

```
Пользователь → Regional IdP
```

Пользователь вводит учётные данные в IdP (Keycloak, Azure AD, AWS Cognito и т.д.).

### 5. Получение authorization code

```
Regional IdP → BFF Service (callback URL)
```

После успешной аутентификации IdP возвращает authorization code в BFF через callback URL.

### 6. Обмен code на токены

```
BFF Service → Identity Provider Gateway → Regional IdP
```

BFF обменивает authorization code на access- и refresh-токены. **Важно**: это происходит на бэкенде, токены не передаются фронтенду.

### 7. Сохранение токенов

```
BFF Service → Token Service
```

BFF сохраняет полученные токены в Token Service в зашифрованном виде.

### 8. Создание сессии

```
BFF Service → Local Identity Store
```

BFF получает или создаёт запись пользователя в Local Identity Store, связывая внешний ID из IdP с внутренним ID.

### 9. Выдача session cookie

```
BFF Service → Frontend (session cookie)
```

BFF создаёт сессию и выдаёт фронтенду только session cookie (HTTP-only, Secure, SameSite=Strict).

### 10. Последующие запросы

```
Frontend → BFF Service (session cookie) → API (с токенами IdP)
```

При каждом запросе:
- Фронтенд отправляет session cookie
- BFF валидирует сессию
- BFF получает токены IdP из Token Service
- BFF делает запрос к API с токенами IdP
- API валидирует токены и обрабатывает запрос

## Безопасность

### Защита токенов

- **Токены IdP никогда не попадают на фронтенд** - только session cookies
- **Шифрование токенов** - AES-256 для хранения в Token Service
- **HTTPS везде** - все соединения зашифрованы
- **Secure cookies** - HTTP-only, Secure, SameSite=Strict флаги

### Защита от атак

- **CORS политики** - строгие ограничения на источники запросов
- **Rate limiting** - защита от брутфорса и DDoS
- **CSRF защита** - использование SameSite cookies и CSRF токенов
- **XSS защита** - HTTP-only cookies не доступны через JavaScript

### Аудит и мониторинг

- **Audit logging** - логирование всех операций аутентификации
- **Мониторинг токенов** - отслеживание использования и подозрительной активности
- **Алерты** - уведомления о необычных паттернах доступа

## Соответствие требованиям

### Унификация доступа

✅ Единый интерфейс для всех пользователей через BFF и IdP Gateway
✅ Запрос данных учётных записей из внешних источников в стране представительства
✅ Поддержка различных IdP через единый Gateway

### Локальное хранение данных

✅ Персональные и медицинские данные хранятся локально в региональных БД
✅ Принцип data residency соблюдается
✅ Минимизация данных в Local Identity Store

### Безопасная работа с токенами

✅ Токены IdP никогда не передаются фронтенду
✅ Токены хранятся только на бэкенде в зашифрованном виде
✅ Использование session cookies для фронтенда

### Поддержка различных IdP

✅ Плагинная архитектура IdP Gateway
✅ Поддержка OAuth 2.0, SAML 2.0, OpenID Connect
✅ Легкое добавление новых IdP

# Безопасность Reports API

## RBAC (Role-Based Access Control)

### Принцип: Пользователь видит только свои отчёты

Все эндпоинты API реализуют строгий контроль доступа на основе `user_id`, извлечённого из токена аутентификации.

## Механизмы защиты

### 1. Аутентификация через Dependency Injection

```python
user_id: int = Depends(get_current_user_id)
```

- `get_current_user_id` - dependency, которая автоматически извлекает и валидирует `user_id` из токена
- Если токен отсутствует или невалиден, возвращается HTTP 401
- `user_id` всегда берётся из токена, а не из параметров запроса

### 2. Фильтрация на уровне SQL

Все SQL-запросы к ClickHouse содержат обязательное условие:
```sql
WHERE user_id = {user_id}  -- user_id из токена
```

Это гарантирует, что даже при ошибках в коде пользователь не получит данные другого пользователя.

### 3. Валидация результатов

Дополнительная проверка на уровне приложения:
- Каждая строка результата проверяется на соответствие `user_id`
- Строки с несовпадающим `user_id` отбрасываются
- Логируются предупреждения о потенциальных утечках данных

### 4. Логирование

Все операции аутентификации и запросы логируются:
- `user_id` извлечённый из токена
- Параметры запроса (даты, фильтры)
- Предупреждения о несоответствиях данных

## Примеры защиты

### Попытка запросить данные другого пользователя

**Запрос:**
```bash
curl -H "Authorization: Bearer user_id:1" \
  "http://localhost:8000/reports?user_id=2"  # Попытка указать другой user_id
```

**Результат:**
- Параметр `user_id=2` в URL игнорируется
- `user_id=1` извлекается из токена
- Возвращаются только данные для `user_id=1`

### Отсутствие токена

**Запрос:**
```bash
curl "http://localhost:8000/reports"
```

**Результат:**
- HTTP 401 Unauthorized
- Сообщение: "Authorization header required"

### Невалидный токен

**Запрос:**
```bash
curl -H "Authorization: Bearer invalid_token" \
  "http://localhost:8000/reports"
```

**Результат:**
- HTTP 401 Unauthorized
- Сообщение: "Invalid or expired token"

## Интеграция с BFF Service

В продакшене `get_user_id_from_token` будет вызывать BFF Service для:
1. Валидации токена
2. Извлечения `user_id` из валидированного токена
3. Получения дополнительной информации о пользователе (роли, права доступа)

## Рекомендации

1. **Никогда не принимайте `user_id` из параметров запроса** - всегда используйте `user_id` из токена
2. **Всегда фильтруйте данные на уровне SQL** - не полагайтесь только на проверки в коде
3. **Валидируйте результаты** - дополнительная проверка на уровне приложения
4. **Логируйте подозрительную активность** - предупреждения о несоответствиях данных
